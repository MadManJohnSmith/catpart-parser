# Evidence: the bag-rep payload carries points, not faces — R-BAG is a point-cloud lever (2026-11-19)

**Date**: 2026-11-19
**Status**: COMPLETE — **documented negative for the mesh lever**. The
carrier the missing-store census named (R-BAG:
`CAT3DBagRep`/`CATSurfacicRep` records + 12-byte float points) holds
declared coordinate arrays and **no face list**: 0 facet/strip records
validate, and the only in-bounds reference lists (3 of 121 rows) read as
edges, not triangles. A viewer can plot the points; it cannot build a
surface. Ceiling measured below; reopen criterion §9.
**Scope**: the 125 report rows of
[`fitness/reports/20261119T035609Z-7dc3ea.json`](../../fitness/reports/20261119T035609Z-7dc3ea.json)
classified `missing-geometry-store` in
[2026-11-19-missing-store.md](2026-11-19-missing-store.md) — **121 CATIA
rows** (119 `kind=part` + the 2 container-less binaries; the 4 non-CATIA
rows are out of scope by construction).
**Method**: read-only byte census over the corpus,
`scripts/triage/probe_bagrep.py` (stdlib + the committed
`catpart.geometry.store`/`facets` measurement infrastructure;
deterministic, manifest order, ~4 s). Data:
[`data/bagrep-probe.csv`](data/bagrep-probe.csv) (one row per census
row), [`data/bagrep-claims.csv`](data/bagrep-claims.csv) (every figure
below is a row there or arithmetic on rows).
**No `src/` change** in this task.

Labels: **fact** = byte-measured here and reproducible from the CSV;
**inference** = interpretation of measured bytes, reasoning shown;
**unknown** = open, carried forward.

## 2. Scope and what "connectivity" means here

The census established the 119 parts carry no stream store, no pool group
and no vertex-record stream, and named the carrier they *do* have: class
records (`CAT3DBagRep`/`CAT3DBagRepT`/`CATSurfacicRep`), `04 04 fd ff`
node records and 12-byte float point runs. This probe asks one question of
that carrier: **does it encode faces?**

In this codebase "faces" is not a vibe — it is one of exactly three
byte-measurable things:

1. **facet records** — `01 <mk 41..4f> <ty> ff` + counts + references,
   the grammar the shipped clean-store and composite decoders run
   (`facets.parse_facet_record`, `composite.parse_strip_records`), whose
   acceptance test is exact tiling header-to-header;
2. **an index list** — integers inside the record's own point space,
   long enough to be a face list and reaching the top of that space (a
   list that never cites the last point is a count table);
3. **the scene-graph list-node table law** — token `ff ff 02 00 01` +
   the 2-bit per-element table (`composite.layout`), which is how the
   composite path recovers written points and the element space its
   facet refs index.

All three are measured below. If none fires, the payload is points.

## 3. The record family (both header generations)

The class records are identical in the two header generations; the
`dual-catalog` and `ff8` split (33 / 88 rows) does not change the carrier.

**Framing (fact).** A record is `u32le namelen` + the ASCII class name
(`CAT3DBagRep` 11 B in 123 records, `CATSurfacicRep` 14 B in 32 records),
then a 5-byte prefix and a code byte. The probe reports those raw bytes and
does **not** assign them meaning — they are listed because a decoder would
have to start here, and because the census's 4-byte `04 04 fd ff` pattern
is only one of the shapes below (so its 101-part count undercounts the
family).

`CAT3DBagRep` — the measured post-name bytes and their tally:

| post-name bytes (first 10) | records |
| :--- | ---: |
| `54 00 00 00 00 14 04 ff ff ff` | 33 |
| `00 00 00 00 00 04 04 fd ff 00` | 31 |
| `00 00 00 00 30 04 04 fd ff 00` | 17 |
| `00 00 00 00 00 40 01 fd ff 00` | 13 |
| `54 00 00 00 30 14 04 ff ff ff` | 12 |
| `00 00 00 00 00 05 04 fd ff 00` | 7 |
| `00 00 00 00 30 40 01 fd ff 00` | 6 |
| `00 00 00 00 00 50 01 fd ff 00` | 2 |
| `00 00 00 00 20 40 01 fd ff 00` | 2 |

So: a variant byte (`00` or `54`), four zero bytes, an optional `30`/`20`,
a **code byte** from `{04, 05, 14, 40, 50}`, then one of three sub-tags
(`04 fd ff`, `01 fd ff`, `04 ff ff … 01`). 78 records take the non-`54`
shape, 45 take the `54` shape.

`CATSurfacicRep` — 15 distinct post-name patterns, all of the form
`XX XX ff ff 00 00 00 00 30|20 04|40 …`, where the 4-byte field is a
negative value (`0xffffffb1` ×17, `0xffffdf84`, `0xfffff09e`,
`0xffffb8f5`, `0xffffee89`, …). Their semantics stay **unknown**.

**Inventory (fact).**

| measure | value |
| :--- | ---: |
| class records | 155 in 13 rows — 78 `CAT3DBagRep`, 45 `CAT3DBagRepT`, 32 `CATSurfacicRep` |
| `04 fd ff` byte-tag occurrences | 103 in 11 rows |
| `04 ff ff ff ff ff 01` occurrences | 45 in 10 rows |
| patch sub-records (§6) | 631 in 43 rows |

Records are short and uniform: the small `CAT3DBagRep` records are
**62 bytes each** and tile a run of six or seven (Plate 64,817→65,189;
Screw 36,168→36,540; `CAAKhwRuleBaseCreate` 232,335→232,769). A
`CATSurfacicRep` follows and is where the payload lives (Plate 4,489 B;
Screw 7,826 B; `CAAKhwRuleBaseCreate` 8,334 B + 19,724 B).

## 4. Connectivity, three ways

### 4.1 Facet / strip records: zero

`facets.FACET_HEADER_RE` over every payload region of the 121 rows:
**0 headers**. Whole file, for completeness: **24 byte-pattern hits in 11
rows, 0 exact tiles** — every hit is a coincidence inside other content,
not the facet family (the shipped readers accept only records that tile to
the next header). This is the same result the census reached from the
other side (0 pool groups, 0 vertex-record streams): there is nothing here
for a facet reader to read.

### 4.2 Index lists: 3 rows, and they read as edges

Test: within each record (or each payload region when the row has no class
record), find integer runs whose every value is below that span's own
point count, that run at least 6 entries, that use a length divisible by
3, that genuinely vary (≥ 4 distinct values, not mostly zeros) and that
**reach the top of the point space** — the test a triangle list or a strip
loop has to pass. Widths and orders: u16le, u16be, u32le, u32be. `u8` is
deliberately excluded: at a point space of a few hundred a six-byte run
below the bound happens at ~1 offset in 100, so a u8 "hit" is noise.

| row | points | hit | values |
| :--- | ---: | :--- | :--- |
| `Ehi_BundleSegment3_2` | 529 | u16be @73,112, 51 refs | `15,17, 35,37, 60,62, 80,82, 102,104, … 510,512, 528` |
| `CAAMaiDumpToolPath123` | 103 | u16be @48,971, 6 refs | `4, 102, 101, 100, 99, 48` |
| `Plate` | 118 | u16be @68,153, 9 refs | `114,117, 102,105, 90,93, 78,81, 48` |

*Inference:* the first and third are **pairs**, not triples (a triangle
list would read `(15,17,35)` and the next triple would straddle two
runs); the second is a descending fan. Whether these are edges of a
wireframe or the rungs of a quad strip is **unknown** — both readings fit,
and neither is bounded by a declaration the file makes. **118 of 121 rows
have no such list at all**, including every mid-size row
(`Screw` 76 pts, `CAAKhwRuleBaseCreate` 187, `Bundle_Segment2` 266); the
one row with the 529-point array is also the row with the longest list
(51 refs).

### 4.3 The list-node table law: nothing to index

The `ff ff 02 00 01` token appears **35 times in 9 rows**, so the
scene-graph list node is present in a few of these files. But the table
law it opens recovers *written points and the element space* — the faces
still have to come from facet records, of which there are 0 (§4.1); and
the census measured **0 pool groups across all 125 rows** (claims
`MS-05`), so the composite seam has no pool to absorb either. The token
buys nothing on L2 here.

### 4.4 The one law that would not need any of the above — strip over the points

If a declared array were stored as two interleaved rings, a triangle strip
would follow from the ordering with no index list. Tested on the three
largest arrays (read under the census's 3-float convention) by comparing
the step to the neighbour with the distance to
the `N/2` partner (a strip makes the partner distance the *width* of the
band, comparable to the step, not 2–4× it):

| array | points | mean step | mean \|p_i, p_i+N/2\| |
| :--- | ---: | ---: | ---: |
| `Screw` | 76 | 17.91 | 28.11 (N/2 = 38, and 23.88 at N/4 = 19) |
| `Plate` | 118 | 48.49 | 122.69 (N/2 = 59) |
| `Bundle_Segment2` | 266 | 69.11 | 266.48 (N/2 = 133) |

*Inference:* the partner distances are 1.6×, 2.5× and 3.9× the steps, and
they grow with the array — the ordering is not a band. (`CAAKhwRuleBaseCreate`
splits as 11×17 and its 22-point arrays are 2×11, so a two-ring reading is
possible *inside* those arrays; but a two-ring array still needs the face
law and the ring pairing to be declared, and nothing in the stream declares
either.)

## 5. The point arrays: what actually is there

**Framing (fact).** An array is accepted only when all four hold: a
`u32le V` with `V % 3 == 0`, `9 <= V <= 3e6` in front of it; the next `V`
f32 at one 4-byte frame are all clean (finite, zero or
`1e-6 <= |v| <= 1e6`); the block **ends** where the clean run ends (the
next word is not a clean float); and the block carries real coordinates
(≥ 50 % non-zero, no run of 64 identical words). The third test is what
makes this a count-first measurement instead of a scan: without it, 14,666
"arrays" framed themselves inside `AnalysisMechfeat`'s quantized region.

| measure | value |
| :--- | ---: |
| declared arrays | **41** in **29** rows |
| f32 across those arrays | **8,373** |
| points by the census's 3-float convention | **2,791** |
| largest array | **529** points / 1,587 f32 (`Ehi_BundleSegment3_2`) |
| next largest (3-float reading) | 266, 228, 187, 187, 166, 125, 118, 118 |
| rows with ≥ 100 points in one array | 11 |
| rows with no framed array | 92 |

The declared count is a **float** count, and the *element shape is not
uniform*: `CAAScrew`'s 198-float array reads as 2- or 1-coordinate groups
terminated by the constant pair `(0.0, 20.0)` —

```
-57.436 -0.849 | 0.0 20.0 | -56.664 -10.16 | 0.0 20.0 | 8.462 | 0.0 20.0 |
-54.371 -19.217 | 0.0 20.0 | 17.519 | 0.0 20.0 | -50.618 -27.773 | 0.0 20.0 …
```

— i.e. the same variable write shape (`[x][y][z]` / `[z]` / `[y][z]`) the
composite path's 2-bit table encodes, minus the table. So these arrays are
**coordinate write streams**, not flat vertex arrays: the float budget is
the hard measure (8,373 f32; max 1,587), and "points" is the census's
3-float convention applied to it.

Byte anchors of the framing (all three reproduced by `--anchor`):

```
Plate.CATPart          count 354 @65252  -> array @65268  118 points
  head (-44.999, -0.118, 0.0) (-44.999, -0.118, 10.0)   (x,y repeated, z 0/10)
Screw.CATPart          count 228 @36603  -> array @36619   76 points
  head (-8.485, 80.677, 25.334) (-8.485, 80.677, 30.178)
Ehi_BundleSegment3_2   count 1587 @61761 -> array @61765  529 points
```

The point base is consistent: little-endian f32 triples on a 4-byte frame,
with the array starting where the count field's payload starts — not
necessarily on a file-aligned boundary (Plate 65,268 ≡ 0 mod 4; Screw
36,619 ≡ 3 mod 4; the record base is unaligned and the count carries the
frame). A `f32`
pair sharing `(x, y)` with `z` toggling 0/10 is the commonest local shape
(Plate: 40 of 59 consecutive pairs), which is what a two-level boundary
sampling looks like — but it stops holding inside the same array (the
plate's outline points do not pair that way), so it is a *shape of the
data*, not a law.

**The census correction (fact).** §5 of the missing-store note reports
"longest run 21,846 points" at `AnalysisMechfeat`. That run starts at
93,957 on the bytes `04 56 8e 3e / 00 00 00 3f / 00 00 00 3f …`: a
repeated `0.5` word in the quantized region at the end of
`CATSeeBodyCont`. A presence detector that chains 12-byte-stride float
triples reads it as 21,846 points; the framed array in that file is **21
points** at 355,857. The corrected carrier sizes are the ones in the table
above — the population's *largest* shape is 529 points, not 21,846.

*Inference:* 8,373 f32 (2,791 points under the 3-float convention) over 29
parts, for parts of 37 KB–1 MB, is wireframe-scale, not
tessellation-scale. A tessellated plate with two
holes at a 0.2 chordal deviation (the 0.2 scalar sitting between the
plate's float count and its array, at 65,264) needs thousands of vertices;
it stores 118.

## 6. The second stream: per-patch sub-records (the one open carrier)

`CATSurfacicRep` records carry a stream the census did not name: a
repeating sub-record

```
30 04 04 ff ff ff d2 d2 50|51
```

**631 of them in 43 rows** (Plate 10 in one record, `CAAKhwRuleBaseCreate`
52, `Bundle_Segment2` 0 — so it is not the class record that brings it).
Flags measured: `0x50` and `0x51` dominate. The tail of each sub-record
holds u16be words: **79,065 words below 1024 across the corpus, max
1,023**.

What is measured, and what is not:

- **measured**: the tag and the two flag values; the u16be word ranges
  (§4.2's three hits sit in `Ehi_BundleSegment3_2`, which carries no
  sub-record at all, and in `CAAMaiDumpToolPath123` (9) and `Plate` (10),
  so the list is not a property of the patch stream alone); and that the
  stream's words are **not** bounded by the enclosing record's point count
  — the plate's `CATSurfacicRep` declares 118 points and its u16be words
  below 1024 reach 768 (row `BR-10`).
- **not pinned**: the field layout. Inside one 91-byte sub-record the
  floats are frame-shifted (bytes `00 00 b4 42` read as 90.0 only at one
  offset, while the neighbouring field is a 1-byte flag), and the
  sub-record length varies (91, 105, 261 bytes in the same record). A
  decode would have to guess both the per-patch vertex space and the
  primitive law, and no candidate validation exists (no declared count
  matches the word count; no pair of patches closes).

So this stream is **named and quantified, not decoded**. It is the reopen
criterion (§9) — and the reason the verdict below says "points can be
plotted", not "there are no index-shaped bytes at all".

## 8. The verdict

**Points only.** Precise statement of what is claimed:

1. **No face list.** 0 facet/strip records validate in 121 rows (§4.1).
2. **No triangle index list.** 3 rows carry an in-bounds reference list;
   all three read as pairs or a fan, none as triples, and 118 rows carry
   none (§4.2).
3. **No implicit face law over the points.** The three largest arrays fail
   the strip/fan/loop geometry test by 1.6–3.9× (§4.4).
4. **What is there:** 41 declared f32 coordinate arrays, 8,373 f32
   (2,791 points under the census's 3-float convention), largest 1,587
   f32 (§5).

What a viewer gets: **a point cloud** for 29 of the 121 rows (and a
wireframe-shaped reference list for 3 of those), and nothing for the other
92 — their payload is the unpinned patch stream (§6) or the feature tree
the census already documented. What it does **not** get, in any row, is a
surface.

**Open rate: 0 / 103 payload-bearing parts.** No row gains geometry from
this lever; L2 does not move (the population's `missing-geometry-store`
class is unchanged at 125 report rows).

**Reopen boundary (a hard line so the negative is not re-litigated):** this
note is a negative for the *mesh* lever, not a claim that the bytes are
empty. The patch sub-records (§6) are explicitly *not* decoded. Anyone
reopening must show a sub-record law that (a) declares or bounds a
per-patch vertex space, (b) yields triples that are non-degenerate and
coplanar-or-smooth, and (c) tiles sub-record to sub-record.

---

## 9. Reopen criterion

Reopen the surface question **only** if a later probe shows any of:

1. an in-bounds **triple** index list — a u16/u32 run of `3·F`
   references that reaches the top of a declared point space and
   triangulates without degenerates — today 0/121;
2. a validated facet record in a payload region — today 0/121;
3. a **pinned patch sub-record** layout: a field in
   `30 04 04 ff ff ff d2 d2 50|51` whose value equals the sub-record's
   point count *and* whose u16be tail stays inside it — today neither
   holds, and the stream's words reach 768 against the plate's 118-point
   record.

Absent all three, this class is a point-cloud carrier and the honest
viewer output is points.
