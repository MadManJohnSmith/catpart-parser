## 1. Executive summary

Before this slice the L3 headline could not land anywhere: the history-row schema typed
`scalars.L3` as `null` only, `runner.py` aggregated L1/L2 and never called the scorer, and
`history.no_regret` required a Dev rise — a first L3 row with a flat L1/L2 had no accepting path.

After it:

- the history row and the per-run report carry the **same** L3 block
  `{"rate", "resolved", "total", "by_outcome"}`;
- the runner scores it with `catpart.fitness.l3.score_l3(...)` from the repository that holds
  `docs/evidence` (derived from the manifest, never the cwd) and **fails loudly** if the scorer
  raises — there is no code path that writes a null L3 over a broken evidence tree;
- `no_regret` compares L3 as a single scalar: introducing it accepts with L1/L2 intact
  (no Dev rise required), a rise accepts, a fall rejects;
- with L3 null on both sides the verdict is the pre-#58 one — the L1/L2 suite's pinned reasons
  still hold — so no re-evaluation of the 14 committed rows changes hands;
- the publisher adds `runs[].l3` to `fitness-history.json` for rows that carry it.

The scalar the runner emits today is **23/23 = 1.0**, by_outcome decoded 14 /
documented-negative 3 / documented-open 4 / candidate 2 / pending-merge 0 — exactly the BR6
scorer's headline ([`2026-11-17-br6-l3-scorer.md`](2026-11-17-br6-l3-scorer.md) §2).

## 2. The L3 row shape — one scalar, no split

```json
"L3": {
  "rate": 1.0,
  "resolved": 23,
  "total": 23,
  "by_outcome": {
    "decoded": 14,
    "documented-negative": 3,
    "documented-open": 4,
    "candidate": 2,
    "pending-merge": 0
  }
}
```

**L3 has no Dev/Held-out pair.** L1 and L2 measure a corpus sample, so the author-grouped split
is what keeps them honest. L3 measures which frozen constructs the project can resolve from
committed evidence — a property of the decoder/evidence set, not of any corpus file — so the
split does not exist for it and inventing a per-split pair would report the same number twice.
The schema description and the `history.py` docstring both say this; `level_scores_from_json`
skips the L3 slot and `coverage_from_scalars` reads it.

`rate` is recomputed from `resolved/total` on every read; the recorded float is never trusted for
a comparison (`Fraction(resolved, total)`), matching L1/L2's count-based rule.

## 3. Schema change — additive inside v0

`scalars.L3` went from `{"type": "null"}` to a nullable object with `rate` (0..1),
`resolved`/`total` (non-negative integers, `total >= 1`) required and `by_outcome` an optional
object of non-negative integer counts. The field stays **required** and `schema_version` stays
`0`: every existing `"L3": null` row is still valid, which is the project's additive-evolution
rule (`src/catpart/schema/__init__.py`).

Validation pinned in `tests/test_fitness_history.py`: null accepted (the 14 committed rows), the
full block accepted, missing `rate` rejected, `rate` outside [0, 1] rejected, missing
`resolved`/`total` rejected, a non-integer or negative `by_outcome` count rejected, and an
L1/L2-only object rejected for its missing required counts (extra keys stay allowed by the
additive rule — the validator does not forbid a split-shaped object that also carries the
required counts).

The same shape was added to `fitness-report-v0.json` so the report carries the identical block
(decision 6). That file is outside this slice's declared ownership; it is a required
consequence, recorded in §9.

## 4. Runner wiring

1. **Root derivation** — `_l3_repo_root(manifest_path)` walks up from the resolved manifest for
   the directory holding `docs/evidence` and returns it; the cwd is never consulted. A manifest
   outside any evidence tree yields `None` (see the fixture deviation in §9).
2. **Scoring** — `_l3_scalar(root)` calls `catpart.fitness.l3.score_l3(root)` and converts the
   score to the row block in `OUTCOME_ORDER`. `L3Error`/`OSError`/any other exception is
   **not caught**: the run aborts before any artifact is written.
   `test_l3_scorer_failure_aborts_before_any_artifact_is_written` proves both halves (exit 1, no
   `history.jsonl`, no `reports/`).
3. **Attachment** — `level_scores_to_json(level_scores, l3_score)` feeds one `scalars` object to
   the report and to the history row, so the two cannot drift; the test asserts equality and
   validates both artifacts against their schemas.
4. **Baseline transition** — the pre-L2 baseline branch (a row emitted before G5) remains L1-only
   and does not evaluate L3: that comparison is the L1 transition, the same precedent the L2
   baseline established.

## 5. The no-regret rule with L3

| baseline L3 | current L3 | condition | verdict |
| :--- | :--- | :--- | :--- |
| null | present | no Dev/held-out fall | **accepted** — `L3 recorded with L1/L2 intact` (no Dev rise required) |
| present | present | current rate **>** baseline rate, no falls | **accepted** — `L3 construct coverage rose` |
| present | present | current rate **==** baseline rate | not an increment: the pre-#58 rule decides (`dev did not rise` unless a Dev level rose) |
| present | present | current rate **<** baseline rate | **rejected** — `L3 construct coverage fell`, even when a Dev level rose |
| present | null | the accepted row's scalar was dropped | **rejected** — `L3 construct coverage fell` (fail closed) |
| null | null | anything | the pre-#58 verdict, unchanged |

Precedence: any Held-out fall outranks the L3 reason (`held-out fell` / `dev did not rise and
held-out fell`), and an L1/L2 Dev fall keeps its own pinned reason unless L3 also fell. The L3
clause never *rescues* a regression and never manufactures an acceptance from a flat rerun.

The acceptance test is `(any Dev rise OR L3 introduced OR L3 rose) AND no comparable split fell
AND L3 did not fall`. With L3 null on both sides the L3 flags are all false, leaving exactly
`any_dev_rose and no falls` — the pre-#58 predicate. `test_l3_null_on_both_sides_is_the_pre_58_verdict`
pins the five pre-#58 outcomes (accepted, L2-only, dev-flat, held-out-both, held-out-with-dev-rise)
and asserts the explicit L3 arguments and the omitted ones return equal `NoRegret` values; the
untouched `tests/test_fitness_l2.py` verdict suite holds the same strings through the runner.

**The committed history keeps its verdicts.** Every one of the 14 rows still validates under the
widened schema and still carries `"L3": null`; `load_last_accepted_row` returns
`20261113T231506Z-c2ab64` (accepted, `L2 dev rose with L1 dev flat`), unchanged. The introduction
is therefore exactly the run this slice enables: a first L3 row against that baseline with L1/L2
flat.

## 6. Publication

`scripts/publish_fitness.py` adds `runs[].l3` to `fitness-history.json`:

```json
"l3": {"resolved": 23, "total": 23, "pct": 100.0, "by_outcome": {...}}
```

additive inside trend `schema_version` 1; rows emitted before the first L3 run publish
`"l3": null`, so an unchanged pre-#58 history renders the same document with one extra null key
(the trend is regenerated from the history, never appended to, and the version-stable additive
rule covers the new key). `resolved`/`total` are validated like L1/L2 counts and a malformed L3
object is a hard `PublishError`. The badge stays **L1** — one headline per level.

**The site has no L3 surface.** `site/index.html` renders the L1 stat, the L2 stat and the L2
trend chart; L3 appears only as a "planned · hardest" capability row, not as a fitness number.
Publishing the field is done; the UI is the remaining **#49** item — do not read this slice as
having a rendered L3 chart.

## 9. Deviations

1. **`oneOf` is not available.** Decision 2 asked for `oneOf [null, object]`, but the project's
   validator (`src/catpart/schema/validate.py`) supports a fixed keyword subset and rejects any
   other checking keyword, so a `oneOf` schema would fail closed on load. The union is expressed
   as `"type": ["object", "null"]` plus `required`/`properties` — exactly the L2 precedent, and
   the validator applies object constraints only to objects. Same guarantees, same tests.
2. **`fitness-report-v0.json` edited.** Decision 6 requires the report to carry the L3 block, and
   the runner self-validates the report against the committed schema; leaving `L3: {"type":
   "null"}` there would abort every real run. The shape is identical to the row's.
3. **A flat L3 is not an increment.** Read literally, "accept when … (L3_INTRODUCED OR current L3
   rate >= baseline L3 rate)" would accept every rerun once L3 exists (23/23 repeats are flat by
   construction), defeating the no-regret rule and contradicting the pinned `dev did not rise`
   verdict. The acceptance predicate therefore requires `L3_INTRODUCED OR L3_ROSE` as the
   increment, with ">= baseline" as the **no-fall** leg. This is documented as a rule-table row
   and pinned by `test_a_flat_l3_is_not_an_increment`.
4. **A manifest-only repository records a null L3.** When no directory above the manifest holds
   `docs/evidence`, there is no evidence tree to score, so the row keeps the pre-#58 null (this
   is the synthetic fixture repository the whole runner suite uses, and it lets those tests stay
   untouched). Once the tree exists, every scorer error aborts the run — the null is only reachable
   where there is nothing to score. The real repository is pinned by
   `test_real_repo_l3_root_and_scalar` (root = repo, scalar = 23/23).
5. **No `l3_*` flags on `no_regret`.** The verdict travels in the pinned `reason` string
   (introduced / rose / fell), keeping the historical `no_regret` object shape byte-identical for
   the L3-null rows instead of adding three always-null fields.
6. **L3 gates; the corpus rate does not.** `docs/ROADMAP.md` (Phase 7 acceptance) says the L3
   headline is reported alongside L1/L2 **under no-regret** and the corpus rate never gates. This
   implementation therefore rejects an L3 fall or a dropped L3 scalar, while the corpus rate stays
   a reported statistic. The earlier design sentence ("reported and never gating … no-regret keeps
   comparing L1/L2 only") was corrected in `docs/agents/br6-graph-design.md` in the same landing;
   this item records the divergence rather than leaving two documents disagreeing.
7. **ADR-0001 relaxation, stated.** ADR-0001 accepts an increment only when Dev rises and
   held-out does not fall. The **introduction** of L3 (baseline null → present) is accepted with
   no Dev rise, because a new level has no prior value to rise from and refusing it would make the
   first L3 measurement unlandable. The relaxation applies only to that transition; once L3
   exists, a flat or falling L3 is not an increment.
8. **Rejection precedence.** Held-out fall > L1 Dev fall > L2 Dev fall > L3 fall. A run that both
   falls on Dev and loses L3 coverage is reported as the Dev regression (the pinned historical
   reason), not as an L3 event that would hide it.
9. **Null reachability is wider than "nothing to score".** The null also occurs when no ancestor of
   the manifest holds `docs/evidence` (e.g. a manifest kept outside the repository) even though the
   repository has evidence. That path needs an explicit `--fitness-dir`; the row carries no marker
   distinguishing it from a pre-#58 row, which is why this note records it.
