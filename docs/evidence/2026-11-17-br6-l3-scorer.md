## 6. Determinism and corpus-free operation

The scorer reads four kinds of committed input and nothing else:

1. the frozen vocabulary CSV (denominator + census columns, sha256-pinned);
2. the declarative `RESOLUTION_REGISTRY` in `catpart.fitness.l3` (the
   per-construct resolution table, a module constant — requirement 4 admits
   either a data file or a module constant, and the exclusive-file list for this
   slice admits no new data file);
3. the claims CSVs its resolved rows cite (`br2-planar-claims.csv`,
   `br3-curves-claims.csv`);
4. the last accepted `fitness/history.jsonl` row (read-only).

No corpus binary is opened, no network call is made, no wall clock enters the
document, and CSV reading is order-stable: two runs produce byte-identical JSON
(`test_scoring_is_deterministic`).

## 7. Detector honesty — what this scorer does NOT discriminate

- **It does not decode bytes.** A construct's verdict is exactly as strong as
  the claim row it cites; the scorer validates the citation's existence,
  uniqueness, path and label — never the claim's measurement. Re-running the
  decode is the owning BR ticket's deliverable, not this slice's.
- **`candidate` counts toward the headline.** The enum (ticket #58) lists four
  adjudicated outcomes and pending-merge as absence; the headline counts every
  adjudicated row. The outcome breakdown is reported so a reader can see how
  much of the coverage is `decoded` (9) versus `candidate` (1) — the scorer does
  not blur them.
- **The label/outcome check is a consistency guard, not semantics.** It rejects
  a citation whose claims label contradicts the declared outcome (e.g. a
  `candidate` row cited as `decoded`), but it cannot tell whether a
  `fact`-labelled row actually justifies "decoded".
- **The corpus rate is file presence, not geometric validity.** It reuses the
  BR1 census columns; nothing here re-validates a face, curve or surface.
- **`pending-merge` is an absence marker, not a status.** It is excluded from
  the numerator, carries no claim id, and fails closed if the expected artifact
  appears while the row is still pending — evidence landing without a registry
  update must not silently under-report the headline.

The discriminating edges carry committed synthetic negatives (no mocks: fixture
copies of the real committed CSVs plus injected registry rows), all in
`tests/test_fitness_l3.py`:

| injected defect | expected failure |
| :--- | :--- |
| resolved row with an empty claim id | `requires the exact claim id` |
| claim id absent from the cited CSV | `... is not in ...` |
| claim id duplicated per scope without `claim_scope` | `appears 2 times` |
| claim scope that matches no row (duplicated id) | `matches 0 rows` |
| declared `claim_scope` the selected unique row does not carry | `not the declared` |
| cited row whose `construct` column names another construct | `attributed to` |
| cited row labelled `candidate` under a `decoded` verdict | `does not justify outcome` |
| cited row with a blank (or absent) `label` | `does not justify outcome` |
| evidence path outside `docs/evidence/` | `repo-relative` |
| unknown construct id in the vocabulary or the registry | `unknown construct` / `missing from the frozen vocabulary` |
| frozen row removed, duplicated, or non-`frozen` | `missing from the frozen vocabulary` / `duplicate construct id` / `not frozen` |
| vocabulary + registry jointly extended to 24 constructs | `frozen denominator is 24` |
| population anchor drift (an off-by-one `observations` value) | `disagrees with the scorer population` |
| pending row pointing at a landed claims CSV | `still pending-merge` |
| pending row carrying a claim id | `cannot carry a claim id` |

## 8. Extension point for the orchestrator (BR4, BR5, BR6 shell)

The only edit needed to resolve a pending construct is its
`RESOLUTION_REGISTRY` row in `src/catpart/fitness/l3.py` — scorer logic never
changes. Replace the pending row's `outcome`, `evidence` and `claim_id` (and add
`claim_scope` when the claim id repeats per scope), e.g.:

```python
Resolution(
    construct_id="SRF-02",
    outcome=DECODED,                                    # decoded / documented-negative /
                                                        # documented-open / candidate
    evidence="docs/evidence/data/br4-quadrics-claims.csv",
    claim_id="<exact row id in that CSV>",
    claim_scope="corpus",                               # only if the id is not unique
    owner="BR4",
    note="...",
),
```

Rows to fill after the merges: `TOP-01`, `TOP-02`, `CRV-06`, `SRF-08` (BR5);
`SRF-02`..`SRF-07` (BR4); `TOP-03` (BR6 shell — the declared expected artifact
`docs/evidence/data/br6-shell-claims.csv` is corrected here if that slice
commits another name). `render_summary`/`to_json` re-derive everything from the
table, so the scoring logic never changes.

Flipping a pending row also refreshes the pins that hold the committed
headline: the real-repo assertions in `tests/test_fitness_l3.py` (headline,
`by_outcome`, per-construct verdicts), the BR6 claims rows and this note's
figures. And `LABELS_BY_OUTCOME` is an exact-token constant: a cited CSV that
uses an older free-text label (`fact (...)`, `established (...)`) must either
match a token in that set or the set is extended deliberately — the table
records which labels justify which outcome, so a new label is a contract edit,
not a formatting choice.
