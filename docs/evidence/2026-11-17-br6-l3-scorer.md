## 3. Outcome enum and the citation contract

| outcome | meaning | citation requirement |
| :--- | :--- | :--- |
| `decoded` | decoder with validated structure landed | claim labelled `fact` / `established` |
| `documented-negative` | closed with a documented negative + ceiling arithmetic | claim labelled `negative` |
| `documented-open` | open with published ceiling arithmetic (Phase 7 accepts it as resolved) | claim labelled `open` / `open (ceiling)` |
| `candidate` | evidence landed, semantics still open | claim labelled `candidate` |
| `pending-merge` | governing per-BR claims CSV **absent** at this commit | no claim id; names the expected artifact |

The right-hand column is the default: an optional `claim_label` on the registry
row replaces it with an **exact-match** declaration. It is required by the
merged BR evidence, because those claims CSVs use their own confidence
vocabularies — BR4 `fact` / `drift (fact)` / `volume anchor` / `upper bound
(row-derived sum)`, BR5 `fact` / `unknown`, the shell slice `fact` /
`ACCOUNTING IDENTITY` — while the outcome table admits only `negative`/`open`
tokens for the closed/open outcomes. A declared `claim_label` must equal the
cited row's label verbatim (a vocabulary change in the cited CSV fails the row
again); it is a pin, never a bypass. `claim_construct` applies the same rule to
a row whose `construct` column deliberately names a sibling construct: SRF-06
inherits SRF-05's classified upper bound, so its row declares
`claim_construct="SRF-05"`; an undeclared foreign attribution is still a
miscitation.

No status without a citation: a resolved row missing its claim id, citing a
claim id absent from the named CSV, citing an id that appears more than once
without a matching `claim_scope`, declaring a `claim_scope` the selected row
does not carry (even when the id is unique), citing a row whose `construct`
column names another construct without a declared `claim_construct`, citing a
file outside `docs/evidence/`, or citing a row whose `label` is empty/absent or
contradicts the declared outcome (or the declared `claim_label`) is rejected
before any headline is produced. All 23 resolved rows verify against exactly one
row of their cited CSV (`BR6L3-19_citations_verified`, 23/23), across 5 distinct
committed claims CSVs (`BR6L3-18_cited_claims_csvs`); 11 rows carry a declared
`claim_label` (`BR6L3-28_declared_claim_labels`) and 1 a declared
`claim_construct` (`BR6L3-29_inherited_bound_citations`).

## 6. Determinism and corpus-free operation

The scorer reads four kinds of committed input and nothing else:

1. the frozen vocabulary CSV (denominator + census columns, sha256-pinned);
2. the declarative `RESOLUTION_REGISTRY` in `catpart.fitness.l3` (the
   per-construct resolution table, a module constant — requirement 4 admits
   either a data file or a module constant, and the exclusive-file list for this
   slice admits no new data file);
3. the claims CSVs its resolved rows cite (`br2-planar-claims.csv`,
   `br3-curves-claims.csv`, `br4-quadrics-claims.csv`,
   `br5-cgm-nurbs-claims.csv`, `br6-shell-claims.csv`);
4. the last accepted `fitness/history.jsonl` row (read-only).

No corpus binary is opened, no network call is made, no wall clock enters the
document, and CSV reading is order-stable: two runs produce byte-identical JSON
(`test_scoring_is_deterministic`).

## 7. Detector honesty — what this scorer does NOT discriminate

- **It does not decode bytes.** A construct's verdict is exactly as strong as
  the claim row it cites; the scorer validates the citation's existence,
  uniqueness, path, attribution, scope and label — never the claim's
  measurement. Re-running the decode is the owning BR ticket's deliverable, not
  this slice's.
- **`candidate` counts toward the headline.** The enum (ticket #58) lists four
  adjudicated outcomes and pending-merge as absence; the headline counts every
  adjudicated row. The outcome breakdown is reported so a reader can see how
  much of the coverage is `decoded` (14) versus `candidate` (2) — the scorer
  does not blur them.
- **The label check is a consistency guard, not semantics.** Without a declared
  `claim_label` it rejects a citation whose claims label contradicts the
  declared outcome (e.g. a `candidate` row cited as `decoded`); with one, it
  rejects any label that is not that exact token. Neither form can tell whether
  a `fact`-labelled row actually justifies "decoded".
- **A declared `claim_construct` is an explicit inheritance, not a silent
  pass.** SRF-06 cites SRF-05's upper-bound row because a surface of revolution
  has no separable bound; the declaration records the sibling attribution, and
  dropping it re-fails the citation. The scorer still cannot tell whether the
  inherited bound is the right population — that is BR4's argument, cited.
- **The corpus rate is file presence, not geometric validity.** It reuses the
  BR1 census columns; nothing here re-validates a face, curve or surface.
- **`pending-merge` is an absence marker, not a status.** It is excluded from
  the numerator, carries no claim id, and fails closed if the expected artifact
  appears while the row is still pending — evidence landing without a registry
  update must not silently under-report the headline. No row is pending at this
  commit (`BR6L3-07`), but the mechanism stays armed for the next BR.

The discriminating edges carry committed synthetic negatives (no mocks: fixture
copies of the real committed CSVs plus injected registry rows), all in
`tests/test_fitness_l3.py`:

| injected defect | expected failure |
| :--- | :--- |
| resolved row with an empty claim id | `requires the exact claim id` |
| claim id absent from the cited CSV | `... is not in ...` |
| claim id duplicated per scope without `claim_scope` | `appears 2 times` |
| claim scope that matches no row (duplicated id) | `matches 0 rows` |
| declared `claim_scope` the selected unique row does not carry | `not the declared` |
| cited row whose `construct` column names another construct | `attributed to` |
| declared `claim_construct` that the cited row does not carry | `not the declared claim_construct` |
| declared `claim_label` that differs from the cited row's label | `labelled ... not the declared claim_label` |
| documented-negative verdict whose row is labelled `fact`, no `claim_label` | `does not justify outcome` |
| cited row labelled `candidate` under a `decoded` verdict | `does not justify outcome` |
| cited row with a blank (or absent) `label` | `does not justify outcome` |
| evidence path outside `docs/evidence/` | `repo-relative` |
| unknown construct id in the vocabulary or the registry | `unknown construct` / `missing from the frozen vocabulary` |
| frozen row removed, duplicated, or non-`frozen` | `missing from the frozen vocabulary` / `duplicate construct id` / `not frozen` |
| vocabulary + registry jointly extended to 24 constructs | `frozen denominator is 24` |
| population anchor drift (an off-by-one `observations` value) | `disagrees with the scorer population` |
| pending row pointing at a landed claims CSV (injected fixture registry) | `still pending-merge` |
| pending row carrying a claim id, scope, label or construct | `cannot carry a claim ...` |

## 8. Extension point after this integration

All 23 frozen rows are resolved at this commit, so the registry is no longer
waiting on BR4/BR5/shell evidence. Adding a new BR still means editing
`RESOLUTION_REGISTRY` in `src/catpart/fitness/l3.py` only — scorer logic never
changes. A new row records its `outcome`, `evidence` and exact `claim_id` (plus
`claim_scope` when the id repeats per scope), and declares `claim_label` when
the cited CSV speaks another BR's label vocabulary; that declaration is the
same exact-match rule this integration introduced, not a new relaxation. A
cross-construct citation (an inherited bound) must declare `claim_construct`.
Then re-run:

```bash
export LD_LIBRARY_PATH=/usr/lib:${LD_LIBRARY_PATH:-}
.venv/bin/python -I scripts/triage/score_l3_constructs.py
.venv/bin/python -m pytest -q tests/test_fitness_l3.py
.venv/bin/python -I scripts/triage/check_claims_csv_quoting.py
```

`render_summary`/`to_json` re-derive everything from the table, so the scoring
logic never changes.

Flipping a row also refreshes the pins that hold the committed headline: the
real-repo assertions in `tests/test_fitness_l3.py` (headline, `by_outcome`,
per-construct verdicts), the BR6 claims rows and this note's figures. And
`LABELS_BY_OUTCOME` is an exact-token constant: a cited CSV that uses an older
free-text label (`fact (...)`, `established (...)`) must either match a token in
that set, be covered by an exact `claim_label`, or the set is extended
deliberately — the table records which labels justify which outcome, so a new
label is a contract edit, not a formatting choice.

## 10. Deviations / notes

- The frozen vocabulary is the BR1 freeze. Its 8 unprovenanced cells are
  disclosed above and in the provenance audit; the scorer quotes them as frozen
  input and never presents them as measured rates. Any future generator drift
  (BR3 §6.3) is a census concern that must be recorded, not silently absorbed.
- `SRF-01` is cited decoded on its plane-validation row (`BR2-10`), with the
  BR2 note's open items (composite index space, surface identity) carried in
  the registry note rather than hidden by the verdict.
- `TOP-06`'s E1 residue remains named (`T06_edge_residue_files`) and is not
  absorbed into the decoded verdict.
- `claim_construct` is the one contract addition this integration needed: BR4's
  `SRF-05_upper_bound_allscopes_presence` carries `construct=SRF-05`, and SRF-06
  deliberately inherits that bound. The declaration keeps the attribution check
  fail-closed (an undeclared foreign attribution is rejected) instead of
  dropping the check or inventing a duplicate claim row.
- The BR5 claims CSV names its population axis `release` (value `all`), not
  `scope`; the scorer reads `scope`, falling back to `release`, so the
  `claim_scope="all"` declarations validate against the merged file.
