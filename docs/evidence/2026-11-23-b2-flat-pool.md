## 2. B2 — the table reading is a phantom with a one-word residue

Both twins carry the same two token nodes (body
`[0x137dc,0x15146)` / `[0x13925,0x15417)`, `CATBRepModeContainer`),
`01 02` + `01 06` composite markers, two 8-vertex pool groups, and this
node-0 header:

```
token ff ff 02 00 01 | c1=26 | c2=22 | 00 00 00 01 | 00 80 99 43 ...
counts_end = 36      table[36:43] = 00 00 00 01 00 80 99
slots (2-bit LSB):   22 x shape 0 (3 words), 2 x shape 1 (skip),
                     2 x shape 2 (1 word)  -> sum(shapes) = 68
write_count byte at 43 = 0x43 = 67      -> sum - write_count == 1
region_start = 44, region_end = 312; the walk dies at element 25.
```

The one-word residue is the signature of the misparse, and the bytes
pin why: **the count byte 0x43 is the high byte of the first x
coordinate.** The store's real layout is the flat law — a 4-B field
`00 00 00 01` at `counts_end`, then `element_count` full f32 triples:

```
flat start = counts_end + 4 = 40
triples[0..2] = (307.0, 90.643959, 73.455956),
                (-106.0, 90.643959, 73.455956),
                (307.0, 80.372383, 60.361561)
first x = 307.0 = 00 80 99 43  <-- the phantom write_count 0x43
```

The 26 flat triples re-list pool group 0 **8/8 verbatim** (the second
group 0/8). The sibling rep (node `0x140c2` / `0x1420b`, c1=91/92) has
the same phantom shape with a larger residue (sum 173/171 vs
write_count 66; diff 107/105 — its count byte lands inside a later
triple), and its 91/92 flat triples re-list pool group 1 **8/8**. The
store therefore has no table-region reading at all; each rep's region
is a flat triple list that re-lists its own pool group.

## 3. The fix — per-GROUP pool re-listing in the existing flat arm

The stage-8 flat arm already had the right acceptance battery
(all-nice under `_nice`, then `x-ascending >= RAW_FIT_RATE` **or** the
pool fully re-listed). Its pool test used the **union** of every pool
group (`poolv`), which a multi-rep node can never satisfy: on the twins
the union is 16 vertices and each region re-lists 8. The fix is one
predicate, no new law path:

```python
pool_hit = any(pset and pset <= pts_set for pset in pool_groups)
if asc >= RAW_FIT_RATE or pool_hit:
```

`_decode_node_mixedwrite` now receives the per-group vertex sets;
everything else — the table extent candidates, the raw arm, the flat
start (`counts_end + 4`), the all-nice predicate, the store-level
diagonal absorption gate, the refs gate and triangulation — is
unchanged. The part still fails closed when no single group is
re-listed or the triples are not all nice. The B2 one-word arithmetic
is the diagnostic that identifies the family; the acceptance stays the
flat battery's own, now applied at the right granularity.

## 7. B3 — STOPPED: the refs are local, and their owner is not pinned

`4902c650` is a multi-body store: body `[0x35a24,0x52449)`, **8 pool
groups** (4, 4, 8, 12, 12, 4, 8, 34 = 86 vertices), 17 token nodes, of
which **5 walk-exact** (66, 8, 90, 8, 34 elements = 206). The
single-rep path fails absorption; the per-rep path pairs group *k* with
decoded rep *k* and fails on rep 0 (refs 83 >= 66) and on reps 1–4
(their groups are not in the paired regions).

The B3 question — are the out-of-rep refs **global across reps** or do
they follow a **`05 08 01` sub-node element-index law**? The bytes say
neither:

- **Local is the only coplanar reading.** Every in-bounds loop of a
  normal-carrying record is coplanar against its stored normal under
  local element indices: **46/46 coplanar, 0 nonplanar** (worst
  deviation 4e-05, `PLANE_TOL` 2e-3). Mapping the same refs into the
  concatenated 206-element space gives **10 coplanar / 51 nonplanar**
  (deviations 3.7–1,340 mm); indexing the `05 08 01` coordinates gives
  **8 coplanar / 53 nonplanar** (deviations 60–2,142 mm). Global and
  sub-node indices are rejected by the battery.
- **The `05 08 01` records are pool re-listings, not an index space.**
  132 records, each `05 08 01` + 12-B f32, chained 15 B apart with **no
  index field**; their coordinates re-list **86/86** pool vertices
  (group by group). The ordinal mapping is exactly the nonplanar S
  hypothesis above — the records pin pool identity, not element
  indices.
- **The out-of-rep refs sit in stray record blocks.** In rep 0's
  territory, two `0x42` records cover refs **0..83** (42 + 42), which
  exceed rep 0's 66 but fit a 90-element space; in rep 1's territory an
  eight-record `0x4a`/`0x42`/`0x4c` block carries **0..89** (the
  `0x4a`/`0x4c` refs reach 81..89) — the same refs as the block inside
  the decoded 90-element rep 2 (`0x39bad..` vs
  `0x3a91b..`; the refs match, the normals differ by a byte). There
  are **two** 90-element nodes (`0x395da`, which walk-fails, and
  `0x3a3f0`, which decodes), and the record blocks carry no owner or
  element-count field. The bytes therefore do not pin which rep owns
  the stray blocks.

Changing the index space would be inventing one, and attributing the
blocks by count alone would be guessing between two 90-element spaces.
**B3 stays `undecoded-variant`; no B3 code change and no index-space
law are claimed.** The remaining work is an ownership/segmentation law
for the interleaved record blocks (and the walk-exact decoding of the
other 90-element node), which is a different lever from the B2
reconciliation.
